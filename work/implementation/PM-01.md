## The defect

`public/js/progress-merge.js` exports `mergeProgress()` and `progressEqual()`. `progressEqual`
was a raw `JSON.stringify(a) === JSON.stringify(b)`, while `mergeProgress()` builds its output
object with a **different key order** than the state it is given. Measured on the base commit
before the fix:

```
progressEqual(state, mergeProgress(state, state)) === false
state  key order: version,createdAt,updatedAt,settings,nodes,history,errors,srs,days,planDone,counters
merged key order: version,createdAt,updatedAt,settings,counters,nodes,history,errors,srs,days,planDone
```

The consequence was not just a wasted payload. `server.js` does
`if (!progressEqual(state, merged)) payload.state = merged;` — always true, so the server
shipped a **full merged state on every POST**, and no caller could use `progressEqual` to answer
the one question it exists to answer: *did anything actually change?*

This defect is the mechanism the SEC-02R review (finding F-2) relied on to explain the reset
resurrection. SEC-05 made that harmless (the `rev` tombstone refuses stale writes and the epoch
discards post-reset folds) but explicitly left `progressEqual` untouched because
`public/js/progress-merge.js` was outside its allowed paths. See `work/implementation/SEC-05.md`.

## The fix

`progressEqual` now compares a **canonical, stable key-ordered serialisation** of both sides
(keys sorted recursively; arrays keep their order because order is meaningful there). This is
the task's preferred option 1: it keeps every call site — including `server.js:483`-equivalent
`if (!progressEqual(state, merged))` — unchanged and fixes every caller at once. `mergeProgress`
and its merge semantics are **untouched** (monotonic counters, newest-wins node selection,
history union), so the protection against a partial write erasing a week of study is intact.

Option 2 (make `mergeProgress` emit a deterministic key order matching its input) was rejected:
`mergeProgress` output is persisted and its field order is part of the stored record, so changing
its shape has wider blast radius for no benefit the comparison cannot deliver on its own.

`server.js` needed **no** change, as the task predicted. The one expression in it is correct once
the comparison is.

### What the new checks cover

`tools/progress-equal-check.mjs` (+ `.test.mjs`), offline and dependency-free (Node built-ins only):

1. `equal-for-fresh-empty-state`, `equal-for-populated-state`, `equal-for-top-level-key-order`,
   `equal-for-nested-key-order` — `progressEqual(state, mergeProgress(state, state)) === true`.
2. `unequal-for-genuinely-different-records` — changed counter, changed node, removed key, added
   key, changed setting, removed history entry all compare unequal; identical pairs still equal,
   so the function is not a constant (a comparison that returned true for everything would pass
   (1) and fails here).
3. `comparison-is-symmetric` — `progressEqual(a,b) === progressEqual(b,a)` for equal and unequal
   pairs.
4. `probe-discriminates-on-prefix-module` — the four check-1 shapes, run against the pre-fix
   module, all return strict `false`.
5. `http-omits-state-when-merge-changes-nothing`, `http-returns-state-when-merge-changes-something`
   — real HTTP against the real server.
6. `prefix-server-returns-state-on-identical-post` — the pre-fix server reproduces the defect.

## A note on "a fresh empty state"

The fresh shape is the app's canonical fresh state (`freshState()` in `public/js/store.js`: a
full-shaped record with empty containers), matching what the client actually POSTs — not the
literal `{}`. A bare `{}` is genuinely *not* logically equal to `mergeProgress({}, {})`, which
legitimately adds the default fields; requiring them to compare equal would demand an always-true
function, which check 2 forbids. The key-order defect is present on the realistic fresh state and
the probe catches it there.
