# PILOT-I18N selected interface language and bilingual directions

Ron explicitly requested this behavior on 3 October 2026: a foreign-language learner can understand the landing page, signup flow and application menus/guidance in their selected language, while original exam-language content remains intact and directions are additionally translated. This supersedes German-only interface preservation. Supported interface languages are de/en/uk/ar/tr. [Issue129](https://github.com/ronslink/hatoove/issues/129) records the work. Independent contract/source review PILOT-I18N-CONTRACT-R1-20261003-C is clear after the recorded race, retry, material-boundary and state-preservation corrections. This frozen contract does not itself lease implementation; separate bounded assignments follow.

## Product boundaries

1. Public landing, sign-in/signup, verification/reset, navigation, account/setup/purchase screens, buttons, accessible names, state messages and app guidance follow the selected interface language. Language selection is visible and keyboard accessible before signup and in the app. Use native language names. Preserve the supplied orange design and vanilla client.
2. Exam package, exam language, interface/explanation preference and purchasing market remain independent. Locale selection changes neither exam nor product, price, date, assessment, answer, purchase or ownership. Existing `settings.language` becomes the interface and preferred explanation language; immutable submission `explanation_language` snapshots remain unchanged.
3. Assessed passages, recordings, questions, answer choices, headlines, advertisements, word banks, writing scenario/addressee/Leitpunkte and learner text stay in the exam language. The generated matching option “Keine passende Anzeige” is assessed text and stays German. Do not translate stored exam payloads or change their hashes/review status.
4. Operational directions appear in the exam language plus the selected-language translation when different. For German selection show one copy. Bilingual operational directions are allowed in timed mocks, without hints or translated answer material. Explicit German/LTR exam islands remain inside Arabic/RTL interface layout. Other future exam languages must be derived from the exam contract, never from interface locale.
5. Existing saved explanation representations retain their source, language, missing/fallback, rights/review and no-new-grading contract. Localize their controls and notices independently of the actual displayed prose. Do not present missing educational or native translations as reviewed or silently translate with a live provider.

Library/reference titles supplied as authored content, vocabulary entries, grammar examples and educational prose remain versioned learning material. Localize library navigation, section-kind labels, controls and the explicit source-language/translation-unavailable notice in all five languages. Preserve existing authored de/en reference alternatives; this slice does not invent a complete translated educational corpus. Operational app help, landing/demo explanations and self-review interface copy are owned UI copy and do receive all five translations. Clearly annotate the actual language of preserved learning material so localized chrome never implies translated prose.

## Shared public locale runtime

Place reusable browser modules under `public/assets/i18n/`, already publicly served. No auth-module access widening. Root owns `core.js` and `common.js`; each author owns a separate dictionary namespace. No package/framework dependency.

Proposed frozen exports from `core.js`:

```js
export const LOCALES = Object.freeze(['de', 'en', 'uk', 'ar', 'tr']);
export const LANGUAGE_NAMES = Object.freeze({de:'Deutsch', en:'English', uk:'Українська', ar:'العربية', tr:'Türkçe'});
export function validLocale(value); // exact enum; boolean
export function initialLocale(); // valid guest scalar, then supported navigator language, then de
export function storedLocale(); // the visitor's OWN stored choice, or null; never guesses from the browser
export function getLocale();
export function setLocale(locale, {persist = false} = {}); // validates, updates html lang/dir, then notifies
export function subscribeLocale(listener); // returns unsubscribe; never accumulates duplicate subscriptions
export function registerMessages(namespace, byLocale); // all five maps; keys/placeholder parity checked offline
export function t(key, params = {}, locale = getLocale()); // namespaced keys, plain text; no HTML evaluation
export function translateDom(root = document); // only explicit data-i18n bindings and whitelisted text attributes
export function formatNumber(value, options = {}, locale = getLocale());
export function formatDate(value, options = {}, locale = getLocale());
```

Only guest persistence is one string scalar, `hatoove.interface-language.v1`, containing an exact locale enum. No owner/email/session/token/route/draft/progress object. Storage denial or malformed data must not break rendering. Never persist browser-detected language until an explicit user selection; selecting a language may persist this scalar. Existing-account login always obtains the server preference; it must not overwrite that account with a leftover guest scalar. Logout may retain the scalar, but clears all account-specific operations and speech. Fresh browsers recover signed-in preference from the server.

`storedLocale()` exists because the public front door must start in the language its HTML already contains. `initialLocale()` guesses from `navigator.languages` when nothing is stored, which is right inside the gated app but wrong on a page whose canonical URL and structured data are German: a crawler reports `en-US` and would be served an English rendering under `<html lang="en">`. The public shell therefore boots as `setLocale(storedLocale() ?? 'de')`, at both the initial call and the bfcache restore, and it never reaches storage itself — the read belongs to this runtime, and `tools/public-locale-check.mjs` fails a shell that does its own.

`t` returns text, and renderers must escape it before interpolating into markup. Parameters are named scalar values; dictionaries contain no event handlers, executable HTML or CSS. `translateDom` supports `data-i18n` (textContent on an explicitly isolated text node), `data-i18n-title`, `data-i18n-placeholder`, `data-i18n-aria-label` and `data-i18n-alt`; it must not replace parents containing inputs, icons or live state. Visible fallbacks must not falsely imply complete translation. All shipped UI namespaces require full five-language key/placeholder coverage before acceptance. Source content is not translated by scanning arbitrary DOM text.

## Preference lifecycle and signup

Authenticated selection uses the existing owner-bound settings endpoint, expected revision and account generation. Apply the new authoritative locale only after a successful save; show localized pending/conflict/error states and preserve the last saved selection on failure. A reply for a previous account/view cannot alter current preference or DOM. If another settings write wins, show conflict and reread before an explicit retry. Never overwrite unrelated theme/legacy preferences.

Serialize settings writes with the existing owner7352 advisory lock before reading/locking/upserting the settings row. `SELECT FOR UPDATE` alone cannot protect a missing settings row: two expectedRevision0 writes must not both succeed. Exactly one competing writer commits; the other returns409 with current state. Retain owner-before-exam-before-tuple ordering and cover deletion interactions. Send only the requested locale patch, not a stale copied theme. After a lost/unknown save acknowledgement, retain the last confirmed UI locale while rereading the same owner's authoritative settings under generation fences; adopt a committed server value/revision without blindly resending or restoring stale fields. A failed reread leaves an explicit unresolved/retry-read state.

Preserve existing submission-language semantics rather than changing grading contracts as part of interface localization. Standalone submission captures the authoritative settings value read by each HTTP attempt before the adapter transaction; it is not a promise to reread at commit. If an earlier attempt never committed, a retry may capture a newer saved preference. Once an event committed, its receipt replay preserves the original saved snapshot and cannot duplicate a job/debit. Mock finalisation instead captures its validated explanationLanguage in the stable action body/request digest; its held or retried body retains that captured value. A concurrent locale save may occur before or after either capture. Never rewrite an existing snapshot, rebuild an in-flight finalise body, change its digest or repeat submission/event/job to impose a later locale. New actions after confirmed locale save use the new preference. Test these distinct orderings, exact request/event identity and the single-job/single-debit boundary. No adapter/mock-writing language-source change is part of this slice.

Signup accepts optional exact enum `language`. Absent preserves compatibility; explicit invalid values are422 with no account/session/settings created. The public signup page sends its selected locale. Initialize the new account preference in the same registration transaction as account, credential, initial preparation/allowance and session. Reserve migration0039 for a narrowly scoped INSERT-only registration-language trigger; do not edit older migration bytes or backfill existing accounts.

The session adapter sets a transaction-local `hatoove.registration_language` to the validated enum or empty for every signup. A separately named pinned-search-path SECURITY DEFINER trigger on AFTER INSERT of the exact user table validates operation/table/schema and locale, returns unchanged for absent language, temporarily binds owner to NEW.id, inserts only that new learner_settings row at revision0 with existing defaults and selected language, then restores prior owner context. No update/upsert of existing settings and no wider auth-role table grants. Revoke public/runtime direct function execution and trigger creation. Rollback at every existing registration hook must remove all new records. This is a local forward migration and disposable acceptance only, not production execution authorization.

No first-boot `revision===0` guest initialization: existing untouched accounts also have revision0. No client two-request initialization race that could write a different signed-in account. Settings/export continue to expose the chosen enum and preserve immutable prior explanation snapshots. Registration locale has no effect on exam, market or initial allowance.

## Bilingual operational directions

Use a versioned instruction registry under `public/assets/i18n/` with an exact German original, source digest, all supported translations and narrowly typed parameters. Select entries by trusted interaction/action identity, not by matching arbitrary content strings or broad family labels. Cover matching headlines/ads, single/grouped choice, gap choice/bank, listening answer/playback, writing assigned/choose-one, mock timing/order and the three public demo directions.

Playback counts and timing come from authoritative DTOs; translation cannot grant extra plays, change deadlines or infer missing values. Unknown instruction type, missing translation or source mismatch preserves the original and shows a localized explicit unavailable notice. No silent English fallback. Current persisted schemas have no dedicated instruction field, so this slice adds translated operational UI directions without extracting from mixed assessed `situation` or question fields. Any future authored excerpt translation needs a separate exact source/version/hash/span binding; no regex or bulk translation of a scenario.

Provide a reusable safe bilingual renderer with explicit language/direction annotations. Rights/review withholding takes precedence: a language switch cannot redisplay protected hidden task/rubric prose. Do not treat original content review as approval of newly authored translations.

Practice author owns `instructions.js` with `instructionMarkup({id, examLanguage, original, parameters = {}, locale = getLocale()})` and `translateInstructions(root, locale = getLocale())`. The registry binds id/version to the exact original template/digest and allowed parameter names/types. The caller supplies trusted exam language and original; unsupported identity/language or an original mismatch cannot select another translation. Output markup escapes every text/parameter and carries explicit instruction metadata for later safe text updates. Unknown entries preserve supplied original text and show the localized unavailable notice. Registered German direction templates come from the reviewed UI instruction types, not arbitrary exam-payload strings. All current interaction types need covered entries; unknown future content has an explicit fallback.

Each existing writing/mock/listening controller adds `updateLocale(locale = getLocale())`; explanation manager adds the same method for controls/notices (its existing `refresh` keeps saved-language read semantics), and checkout controller adds a label-only equivalent. These methods patch existing labeled nodes/attributes and direction annotations from state, without `mount`, `open`, whole-panel `render`, DOM replacement of live controls or network mutations. They preserve input/audio element identity, caret/focus/selection, composition, selected answers, playback position, monotonic clock anchors and event IDs. Initial/state-transition renders remain free to construct views normally. The shell calls these hooks on one confirmed locale event; owners coordinate exact calls before integration. Locale listener disposal and detached-node handling are required.

Locale changes must not remount active audio, editors or timed attempts; reset forms/answers; rotate event IDs; create jobs/intents; repeat a debit; renew timing; or trigger grading. Update only labels and operational text around existing state. Saved explanation reads may follow the existing read-only language-selection contract with its stale-response fences. Speech cancels when its visible text/language or account changes.
