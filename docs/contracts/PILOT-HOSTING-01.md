# PILOT-HOSTING-01 — production preparation contract

Status: reviewed and frozen for bounded implementation, 4 October 2026, issue [135](https://github.com/ronslink/hatoove/issues/135). Base `5435f40ef8e98578cfc695b637ef9740a438043d`. Independent A/B/C reviews cleared the substantive draft SHA256 `ae7f89c6e2da5774add2756b1a9ccc21f100b30cade7c021a84a9f934a9800a6`; this status line records their verdicts. This contract prepares code and configuration; it is not deployment or product acceptance.

## 1. Runtime and authority

Retain the vanilla Node application, a separate sequential worker, one-shot migrations and PostgreSQL under Docker Compose. Ron selected a DigitalOcean Basic Regular 2 vCPU / 4 GiB / 80 GiB Droplet in LON1 at $24/month, with later resizing subject to measurements. Cloudflare fronts one canonical origin, `https://hatoove.com`. No Vercel/framework migration, second application origin, live provider/payment/email call, learner-data mutation, automatic role-password rotation or existing-volume replacement belongs to this slice.

Database placement is not selected. Supply two explicit production configurations: private same-host PostgreSQL with password/SCRAM authentication and retained volume; or external managed PostgreSQL with certificate-verified TLS. Preserve Paykey/Typeforge and their users/trusted sources. A logical database does not isolate shared CPU, I/O or connections. No managed-provider privileges or spare capacity are assumed.

## 2. PostgreSQL connection configuration

Retain existing local defaults and literal password environment variables. Add explicit configuration shared by admin and restricted-role pool builders:

Preserve the exported configuration/pool caller interfaces used by retained checks, including supplied `config.admin` fields and explicit lowering caps. Never use a hidden cached configuration to bypass a deliberately supplied malformed admin endpoint. Strict password validation uses the explicit selected credential, not an ambient `PGPASSWORD` fallback.

- `OWNAPI_PG_TLS_MODE=disable|verify-full`, default `disable` for retained local execution. Always pass an explicit SSL option, so ambient `PGSSLMODE` cannot weaken verification or override the selected mode. `verify-full` requires certificate-chain and `OWNAPI_PG_HOST` identity validation; no arbitrary servername or verifier override.
- `OWNAPI_PG_TLS_CA_FILE`: optional mounted PEM trust bundle for `verify-full`; unreadable, empty or malformed configured CA fails before connecting. Omission uses Node's default trust roots under the pinned runtime configuration, not an assumed OS trust store. A CA file with TLS disabled is a configuration error.
- `OWNAPI_PG_CONNECT_TIMEOUT_MS`: optional strict decimal integer from 250 through 30000; retained local behavior if absent. Production Compose specifies 5000. The readiness probe retains its fixed 1500 ms limits; no new global statement timeout.
- `OWNAPI_PG_POOL_{AUTH,LEARNER,WORKER,DELETION,PAYMENTS,PROVISIONER,ADMIN,MIGRATION}_MAX`: strict decimal integers 1–10; retained defaults respectively 4,4,4,4,4,2,2,2. `OWNAPI_PG_WORKER_RUNNER_POOL_MAX` is separately 1–10, default 2. Readiness is a separate learner pool of maximum 1.
- Pool builders select a named allocation: app-role by default, standalone worker-runner only for the worker role, or migration/admin as appropriate. Configured allocation is authoritative. An explicit caller cap may only lower it and must remain within 1–10; it cannot bypass the allocated ceiling. Refactor hard-coded runtime, provisioner, migration and worker callsites so they neither ignore configuration nor accidentally apply the app-worker maximum to the standalone runner. Readiness deliberately remains maximum 1 and is always included in the budget.
- `OWNAPI_PG_APP_REPLICAS` and `OWNAPI_PG_WORKER_REPLICAS`: declared strict positive integers 1–10, default 1. Validate role totals against the existing role `CONNECTION LIMIT 10`: learner includes readiness for each app, worker includes both app and standalone runner pools, and the other runtime roles include declared app replicas. Admin and migration pools each remain bounded. These declarations must match deployed replicas; this configuration cannot discover other installations.
- `OWNAPI_PG_CONNECTION_BUDGET`: optional strict positive integer 1–1000 for retained local execution, required by production Compose. Reject an aggregate configured ceiling above the explicitly allocated budget, including all declared apps, workers, the readiness pools and one concurrent admin + migration operation. This allocated budget must fit measured spare database capacity after existing applications and maintenance headroom; the code cannot establish that external fact. The retained defaults produce 23 app + 2 runner + 4 deployment = 29 for one app/worker.
- `OWNAPI_PG_REQUIRE_PASSWORDS` accepts absent/0/1 only. Value 1 makes the actual connection being opened require a password; production Compose always sets it. The migrator also preflights valid credentials for every absent role before its first provisioning DDL, because it creates these LOGIN roles without opening their pools. Existing role passwords remain untouched. Local fixtures may retain existing no-password trust mode. Do not require unused admin/migration or other role secrets in an app/worker process.

Add only `OWNAPI_PG_PASSWORD_FILE` and the seven named `OWNAPI_PG_<ROLE>_PASSWORD_FILE` inputs. Treat a literal and file setting for the same credential as a conflict even if one is empty. Resolve secrets lazily for the actual connection, with the narrow migrator-only exception for credentials of absent roles it will create. Reject missing/empty/invalid files and values with fixed redacted errors, and never log contents, connection strings or secret-bearing objects. Define file format as one nonempty UTF-8 password, 1–4096 bytes after at most one terminal LF or CRLF is removed; raw file size is at most 4098 bytes. Reject embedded newline, NUL and malformed UTF-8. Keep passwords out of source, process arguments, images, generated Compose output and tracked artifacts. Do not change existing role grants, RLS, ownership, migration checksums, schema search paths, role connection limits or automatic password-rotation behavior.

## 3. Session-cookie security

Thread trusted `B1PREP_PUBLIC_ORIGIN` through the account fixture/session factory, using one shared origin parser for server and direct account-runtime entry points before any pool is opened. A present nonblank value must be a canonical absolute http or https origin (optionally one terminal slash), with hostname, no credentials, query, fragment, non-root path, whitespace or backslash. Accept only the URL's canonical origin string or that string plus `/`; reject malformed and noncanonical input with a fixed redacted configuration error. Absent/blank remains unconfigured for retained local fixtures; `B1PREP_SAAS=1` alone retains that local fixture behavior. Add `B1PREP_REQUIRE_HTTPS=1` to require a present valid HTTPS origin before pool creation; absent/0 are the local default and other values are invalid. Production Compose always sets this flag.

An HTTPS configured public origin adds `Secure` to both session issuance and clearing. Retain the cookie name, Path, HttpOnly, SameSite, expiry, session/account fences and local HTTP behavior. Never derive Secure from supplied forwarded headers, request Host or request origin. Tests must exercise issue and clear through the account path for HTTPS and local HTTP, spoofed forwarding headers, missing/invalid strict production origin before pools, and retained session behavior. A failed parser must not leak newly opened pools.

## 4. Production Compose and ingress

Add a separate production Compose base plus explicitly selected local-PostgreSQL and managed-PostgreSQL overrides. Preserve `compose.yaml` as the supported local developer path and preserve existing volumes. Use one app and one standalone worker for the initial profile, and make declared replica assumptions visible. Compose service configuration must match the database budget calculation.

- App: restricted runtime role credentials only; no admin/migration secret. Worker: worker credential only. One-shot migrator: bootstrap admin, migration and the role-password inputs necessary to provision the restricted roles, with no live provider credentials. Explain that initialization sets passwords for absent roles and does not rotate existing ones.
- Use read-only mounted secret files from operator-chosen external paths. Repository `.env` is not mounted or copied. The local database uses SCRAM/password authentication, a named retained volume, no host port and an appropriate health gate. The managed variant has no dependency on a nonexistent local database and requires `verify-full` with its actual DNS endpoint and optional CA mount.
- Successful migrations gate fresh app and worker startup in both variants; startup refuses a stale schema. Compose dependencies do not stop previously running instances and existing readiness only probes database availability after startup. The upgrade procedure must explicitly stop/drain app and worker, run a fresh one-shot migrator (never reuse an old successful container as evidence), and start app/worker only after actual success. A failed upgrade leaves both stopped. Prove this sequence starting from previously running services. Never auto-run a production migration from a local test or compensate for insufficient provider privileges by widening runtime grants.
- Set `B1PREP_SAAS=1`, `B1PREP_ACCOUNTS=1`, `B1PREP_REQUIRE_HTTPS=1`, `B1PREP_CONTENT_MODE=public`, `B1PREP_PUBLIC_ORIGIN=https://hatoove.com`. Keep the unapproved-content policy and rights restrictions. Production credentials/provider/legal decisions remain operator inputs; the existing deterministic worker grader is a deployment blocker until the separately evaluated provider contract is implemented, not acceptable production feedback.
- Ingress: Cloudflare HTTPS → Caddy HTTPS → Node on private Docker HTTP port 4321. Only Caddy publishes origin 443 and, if required by the chosen public-ACME bootstrap path, port 80. PostgreSQL, Node and worker do not publish ports. Preserve canonical Host, Origin, Referer, Cookie, X-Hatoove-Account and raw webhook request bytes. Reject unconfigured hostnames. Do not trust arbitrary forwarded IP/proto headers or alter authorization.
- Use stock Caddy with public ACME certificates and an explicit HTTP-01 challenge path as the documented default; disable its direct TLS-ALPN challenge because proxied Cloudflare terminates TLS. Persist certificate state. Both bootstrap and renewal require authoritative DNS to the proxied origin, reachable origin port 80, and unchanged forwarding of `/.well-known/acme-challenge/` through Cloudflare without cache/challenge/redirect. In this profile leave Cloudflare's blanket Always Use HTTPS off; Caddy handles HTTP-to-HTTPS redirects while serving ACME challenges first. Keep Full (Strict) throughout; never bootstrap by weakening it. Prepare ingress/challenge routing before authorized apex DNS, obtain and verify the certificate, and only then expose the accepted app. Document a mounted Cloudflare Origin CA alternative only as an explicit operator choice with trusted-proxy-only browser behavior, expiration/renewal handling and separately secured key storage. No DNS API credential or custom Caddy module is assumed.
- Preserve existing API/private media no-store directives, Range GET/HEAD, 206/416, Content-Range/Length, ETag and per-request authorization. No direct content/exams file server, request-body transformation, login/bot challenge on Stripe webhooks or mutation retry. Retain the 64 KiB application body limit. Any added timeout must allow existing Stripe timeouts and long audio transfers; avoid unrelated global timeout changes.
- Cloudflare bypasses cache for /api and its prefix, /app and its prefix, actual sign-in/reset/verify documents and session-cookie requests. No cache-everything rule. Minimal compatible headers may be specified; do not introduce an untested restrictive CSP, HSTS preload or blanket subdomain commitment.

## 5. Acceptance and evidence

Offline configuration tests prove invalid modes/CA/host-related configuration, ambient SSL downgrade resistance, strict numeric bounds, declared role and total budgets, secret conflicts/missing/invalid/redacted cases, unused-role isolation and unchanged local defaults. Exercise actual pool builders and the worker selection, not a separate mirrored parser. Real disposable TLS PostgreSQL acceptance must demonstrate a valid connection and failures for untrusted CA and wrong host, with exact cleanup; stub assertions alone do not prove certificate verification.

Cookie acceptance exercises actual issuance and logout clearing with trusted HTTPS versus local HTTP and spoofed forwarding headers. Production Compose validation proves both merged configurations, credential mounts/role separation, published ports, migration dependencies and public content policy without printing resolved secrets. Disposable source-only integration must show successful startup, failed migration withholding app/worker, database/schema readiness refusal and exact teardown. Ingress acceptance must cover canonical and foreign Host/Origin, cookie lifecycle, private authorized and unauthorized media Range, and signed synthetic Stripe webhook bytes without live providers.

Run the seven current AGENTS baseline checks and focused retained suites appropriate to changed seams. Browser/PG/Docker work needs a separately bounded disposable execution lease, isolated ports, no learner `.env`, data or volumes, and independent cleanup verification. Desktop/phone screenshots are required only if UI changes; this slice should not alter learner UI. Independent author-excluded reviews and seven required hosted checks precede merge. Preserve test limitations and distinguish delivered, independently reviewed, CI green, merged and product accepted.

## 6. Operator runbook and remaining gates

Document build/start/migration order, service credential matrix, certificate bootstrap/renewal, firewall and SSH-key handling, health checks, rollback and database compatibility limits, encrypted off-host backup and restore rehearsal, and a synthetic load/soak plan for 50→100→200 concurrent learners. Require independently generated distinct bootstrap-admin, migration and runtime-role passwords; mounting the same privileged password under several role filenames does not establish credential separation. Report pool waits, DB connections/locks, worker queue age, error rate, p95/p99, event-loop delay, RSS and CPU/steal time. Do not claim capacity from VM specifications or functional checks.

Deployment, exact database selection, extra recurring spend, backups/restore objectives, real email/provider configuration, production payment activation and security/privacy/legal/content/native/device acceptance remain explicit decisions or evidence gates. Code preparation does not close them. Human approval of actual content remains independent of operational access.
